# 容量模型、经验系数与水位扩容阈值

## 经验系数表（capacity_calc.DEFAULTS，均需实测修正）

| 系数 | 默认 | 依据 | 修正方法 |
|------|------|------|----------|
| CK 压缩比 | 5:1 | 列存 ZSTD 典型值（3~10 视列类型） | `system.parts` 的 compressed/uncompressed 实测 |
| CK 磁盘冗余 | ×2 | 合并期新旧 part 并存 | 观察 merge 队列峰值 |
| Kafka 单分区吞吐 | 10 MB/s | 顺序写经验值（HDD 更低） | 压测 producer 端 |
| Flink 单 slot 吞吐 | 5000 rec/s | 中等复杂度算子 | 反压出现点即上限 |
| RocksDB 放大 | ×3 | 块缓存+memtable+SST 开销 | state backend 监控 |
| 服务时延→线程 | QPS×时延×1.2 | Little's Law | P99 实测 |

## 水位与扩容阈值（50/70 规则）

1. **50% 预警**：磁盘/CPU/分区数/连接数任一水位过半 → 复盘增长曲线，准备扩容方案。
2. **70% 扩容**：过七成必须动作——扩盘/加节点/下调 TTL/缩保留期/加分区，不允许"再等等"。
3. **结构性水位**：CK 活跃分区 >1000（过度分区）、Flink 持续反压 >5min、Kafka 消费 lag 趋势性增长 → 无视百分比立即处理。
4. **容量评审点**：业务量级 ×2 演练一次（预演扩容动作与回滚）。

## 压测验证要求（数字不落地即纸上谈兵）

- 容量结论必须附"如何验证"：生产影子流量或回放压测，观察目标水位与 P99；
- 压测用真实数据分布（倾斜键、热点分区），非均匀假数据；
- 上线后首周按日复核水位曲线与预测偏差 >30% 即修正系数。

## 敏感性速查

- CK 存储 ∝ 行宽 × TTL / 压缩比（三者线性，压缩比反向）；
- Kafka 分区数 ∝ 消息速率（分区数决定消费并行上限，宁多勿少但 repartition 代价大）；
- Flink 并行度 = max(吞吐线性, 键基数开方)；内存 ∝ 状态 ×3；
- 通用线程 ∝ QPS × 时延（时延恶化 2 倍 = 需要线程翻倍 = 雪崩前兆）。
