# 代码评审礼仪与意见措辞模板

## 什么算"合适"的代码意见

1. **对事不对人**：评论指向代码与行为（"这段逻辑"），不指向人（"你怎么"）。
2. **可执行**：每条意见带具体改法或替代方案；只说"不好"不给路径是无效评论。
3. **说依据**：引用规则/规范/事故案例，而不是"我觉得"。
4. **分级明确**：阻断（安全/正确性）与 nit（风格）严格区分，nit 明确标注"可后续处理"。
5. **留有余地**：不确定的用提问式（"这里是否考虑过 X？"），把讨论空间留给作者。

## 意见结构模板（问题-影响-建议-依据）

| severity | 模板要点 |
|----------|----------|
| critical | **[阻断]** 问题 + 证据 + 影响 + 建议 + 依据 + "合入前需要解决" |
| high | **[应修]** 问题 + 建议 + 依据；可允许拆 follow-up 工单 |
| medium | **[建议]** 不阻塞，但建议本轮处理 |
| low | **[nit]** 明示"可改可不改"，避免 nit 刷屏 |

开场："总体看这个变更方向没问题，以下是几点建议："
收尾："以上按优先级排列；有不同意的地方欢迎讨论。"

## 语气红线（tone_check 检查项）

| 类型 | 反例 | 改法 |
|------|------|------|
| 攻击性评价 | "这写得太差了" | "这段逻辑在 X 场景下会 Y" |
| 人身指向 | "你又错了" | "这处实现" |
| 绝对化 | "必须改成这样" | "建议…，依据是…"（安全/正确性问题除外） |
| 反问质问 | "怎么会用这个？" | "这里是否考虑过 X？" |
| 翻旧账 | "说了多少次了" | 聚焦当前变更 |

## 分歧与回复

**评审者**：先理解作者意图（提问 → 引规范 → 给选项）；作者有更完整上下文时，记录结论并放行。
**作者（committer）回复三模板**：
1. 接受："'X' 已在 <commit> 修复，感谢指出。"
2. 部分接受："本轮修主问题，剩余拆 follow-up：<工单>。"
3. 说明背景："这样写是因为 <原因>，已补充测试/注释；仍有顾虑可再讨论。"
